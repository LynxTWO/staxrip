# Approval Packets

## FrameServer Win32 string conversions

- **Area and files:** `Source/FrameServer/Common.cpp`.
- **Protected category:** Native frame-server boundary.
- **Why the risk matters:** Script paths cross from managed Unicode strings into AviSynth ANSI or VapourSynth UTF-8 input. Error messages cross back into managed code.
- **Current evidence:** Seven Release x64 C4267 warnings are reproducible. `WideCharToMultiByte` returned 0 with `ERROR_INSUFFICIENT_BUFFER` while the current helper still returned the bytes left in its buffer. `GetWinErrorMessage` returned 2,048 bytes with NUL padding.
- **Smallest edit after approval:** Check that source lengths fit the Win32 `int` parameters, use the same explicit source length for the sizing and writing calls, reject failed or inconsistent conversion counts, and resize the Windows error string to the returned length.
- **What could break:** Empty strings, non-ASCII paths, replacement-character behavior, or callers that accidentally depend on NUL padding.
- **Verification plan:** Completed with one differential probe, four x64 compile gates, and the representative runtime matrix in `Docs/Verification/FrameServer-Runtime-Gate.md`.
- **Rollback plan:** Revert the `Common.cpp` commit.
- **Human decision required:** The user approved the native-boundary edit on 2026-08-10. Upstream maintainer review remains pending in draft pull request #1987.
- **Remaining unknowns:** The repository has no checked-in focused FrameServer test target. The representative matrix passed, but arbitrary plugins, scripts, media, and full GUI workflows remain outside its scope.

## VapourSynth metadata narrowing

- **Area and files:** `Source/FrameServer/VapourSynthServer.cpp`.
- **Protected category:** Native ABI, frame ownership, and managed interop.
- **Why the risk matters:** The source API permits wider metadata than the existing COM contract. Unchecked narrowing can turn positive frame-rate or stride values negative.
- **Current evidence:** Three Release x64 C4244 warnings are reproducible. The R79 declarations and StaxRip interop layouts establish the type mismatch. A target-toolchain probe reproduced negative results above `Int32.MaxValue`.
- **Smallest edit after approval:** Keep the ABI unchanged. Reject out-of-range frame-rate components during `OpenFile`. Reject an out-of-range stride during `GetFrame`, free the newly acquired frame, clear the returned data pointer, retain a specific error, and return `E_FAIL`.
- **What could break:** A script with an extreme but valid 64-bit frame-rate ratio would fail to open instead of receiving wrapped metadata. A frame with an extreme stride would fail deterministically instead of reaching managed bitmap code with a negative pitch.
- **Verification plan:** Completed with a controlled VSScript double, an in-process `FrameServer.dll` host, four x64 compile gates, and normal-path R73 and R79 runtime cases. Unsupported x86 coverage is not a gate.
- **Rollback plan:** Revert the `VapourSynthServer.cpp` commit. No structure or interface layout change is proposed.
- **Human decision required:** The user approved deterministic rejection on 2026-08-10. Upstream maintainer review remains pending in draft pull request #1988.
- **Remaining unknowns:** Maintainer intent for oversized metadata is unknown. The controlled fake activated the stride branch, but no real R79 frame with an oversized stride was created.

## FrameServer x64 intermediate directory

- **Area and files:** `Source/FrameServer/FrameServer.vcxproj`; `.gitignore` is evidence but does not need an edit.
- **Protected category:** Build configuration and native frame-server output layout.
- **Why the risk matters:** The current Visual C++ default leaves 42 compiler intermediates in an untracked nested directory. A project-file mistake could instead break incremental or parallel compilation.
- **Current evidence:** MSBuild evaluates x64 `IntDir` as `FrameServer\x64\<Configuration>\`, while both Win32 configurations explicitly use `$(Platform)\$(Configuration)\`. The repository has ignored the direct `Source/FrameServer/x64` path since the native project was added. Concrete x64 path overrides passed Debug and Release builds and did not change tracked or untracked status.
- **Smallest edit after approval:** Add `<IntDir>$(Platform)\$(Configuration)\</IntDir>` to the Debug x64 and Release x64 property groups. Leave output paths, toolchain settings, solution mappings, and `.gitignore` unchanged.
- **What could break:** A malformed path could collide configurations, trigger shared PDB failures, or prevent the linker from finding resources and objects.
- **Verification plan:** Rebuild Debug and Release x64 with the project edit, assert the evaluated `IntDir` and unchanged `TargetPath`, inspect logs for C1041 or LNK1181, and require a clean worktree outside ignored outputs.
- **Rollback plan:** Remove the two added `IntDir` elements.
- **Human decision required:** The user approved the two-element project-file edit on 2026-08-10. It is implemented as commit `bf855df7` in draft pull request #1989; upstream maintainer review remains pending.
- **Remaining unknowns:** No unknown blocks the x64 edit. The user confirmed that current StaxRip builds are x64-only. Legacy x86 configurations were left untouched and were not used as a gate.

## Keep the VapourSynth library alive for the process lifetime

- **Area and files:** `Source/FrameServer/VapourSynthServer.cpp` and `Source/FrameServer/VapourSynthServer.h`.
- **Protected category:** Native frame-server lifetime and dynamic-library boundary.
- **Why the risk matters:** The first server instance unloads `VSScript.dll`, while a process-wide resolved flag and function pointer remain. A later server skips loading the library and calls through the stale pointer, terminating the process.
- **Current evidence:** A focused x64 host created, opened, read from, and released two VapourSynth servers sequentially. The unchanged build failed during attempt 2. Source inspection tied the failure to `wasResolved`, the global `vss_getVSScriptAPI` pointer, and per-instance `FreeLibrary` ownership. A first per-instance repair passed packaged R73 but failed R79 sequential initialization, proving that unload and reload is not a valid cross-version contract.
- **Smallest edit after approval:** Load and resolve VSScript under one process-wide mutex. Retain one validated module handle and entry point until process exit. Keep failed loads and missing entry points retryable. Preserve the exported COM interface, VapourSynth API version, architecture-specific export lookup, error strings, and frame cleanup order.
- **What could break:** Failure retry or overlapping server instances if initialization is not serialized, or resource expectations if a caller depends on unloading VSScript before process exit.
- **Verification plan:** Completed four controlled lifecycle cases: sequential use, recovery after script failure, recovery after a missing runtime becomes available, and overlap. Also completed four x64 build gates; packaged R73 and AviSynth native and managed-host cases; R79 compatibility cases; and the combined gate with draft pull requests #1987 and #1988.
- **Rollback plan:** Revert the two-file native commit.
- **Human decision required:** The user approved the native lifetime fix and dependency staging on 2026-08-11. Commit `eec333a3` is in draft pull request #1993; upstream maintainer review remains pending.
- **Remaining unknowns:** The representative matrix passed. The full StaxRip GUI, arbitrary third-party plugins and scripts, and long-running resource behavior remain untested.

## Concurrent callers of the script synchronization guard

- **Area and files:** `Source/Video/VideoScript.vb:287-317`. Context, not edited: `Source/General/GlobalClass.vb:631-651`, `Source/General/Extensions.vb:622-638`, `Source/Forms/MainForm.vb:3763-3790`.
- **Protected category:** Concurrency and shared-resource coordination, named in `AGENTS.md` under approval-gated areas. The same edit also sits on the script-generation path, which is a product promise.
- **Why the risk matters:** During a chunked encode, several encoder workers run `VideoScript.Synchronize` at the same time whenever the script contains a macro whose expansion changes between calls. Three things follow. Colliding writers to the same script file retry ten times at 150 ms in `Extensions.WriteFile`, which stalls a worker for up to about 1.5 seconds, and a writer that exhausts the budget calls `g.ShowException` at `Extensions.vb:634`, raising a modal dialog from a worker thread. `Info`, `OriginalInfo`, `Error`, `LastCode`, and `LastPath` are read and written with no synchronization. And `g.MainForm.Indexing()` runs on a `Parallel.Invoke` worker, where it assigns Windows Forms control properties without marshalling.
- **Current evidence:** Established by source reading in `Docs/Review/Chunk-Encode-Synchronize-Concurrency.md` and then observed on the shipping v2.52.5 x64 release binary in `Docs/Review/Chunk-Encode-Synchronize-Runtime-Confirmation.md`. Eight threads were simultaneously inside the guarded body in the treatment case and none in the control. The probe and its run log are committed on `agent/chunk-sync-runtime-proof`. The observation also corrected the earlier source reading: colliding writers do not interleave into a corrupt file, they take the retry path described above, so a fix must address `g.ShowException` on a worker thread and not only the write itself.
- **Smallest edit after approval (revised 2026-08-24):** Make the guard's comparison deterministic. The guard is a cache check whose key changes on every read: `LastCode` holds the output of `Macro.Expand` at `VideoScript.vb:287`, and the guard compares a freshly expanded value against it, so a script containing a time or random macro can never match. Restoring the short-circuit stops worker threads from entering the body at all, which closes all four consequences with no lock and no new blocking. Ship the revert-mutation proof in the same change: undo the fix, record the probe returning 8 of 8, restore it, record 0 of 8.
- **What was ruled out, and why the earlier proposal changed:** The first version of this packet proposed a `SyncLock` around `VideoScript.vb:289-317` and flagged a possible deadlock. That question is now answered and the answer is no; the full trace is in `Docs/Review/Evidence-Gap-Check.md`. MainForm marshalling is asynchronous, the one synchronous blocking `Invoke` targets a thread that cannot re-enter, and the nested `SyncLock Procs` creates no AB-BA cycle. The lock was withdrawn for a different reason the same trace exposed: the guarded body contains two modal dialogs, at `Package.vb:2976` and `Extensions.vb:634`, and one unbounded external wait at `Proc.vb:320`. A lock held across those freezes every UI-thread caller of `Synchronize` for as long as a dialog goes unanswered or an indexing job runs. That is recoverable where a deadlock is not, but a user cannot tell them apart. Serializing also fixes only two of the four consequences.
- **What could break:** Changing the cache key changes when scripts are legitimately rewritten. A key that is too stable can leave a stale script on disk after an edit that should have triggered a rewrite, which is a correctness risk pointing the other way. This is the substance of the decision below and needs the maintainer to weigh it, because the guard's intended refresh semantics are not documented anywhere in the repository.
- **Verification plan:** Re-run the existing barrier probe against a build carrying the lock and require 0 of 8 threads inside the body in both control and treatment, plus the revert-mutation red run recorded before the fix lands. None of this can run in the current environment, because the managed project does not build here; that blocker is recorded as its own unknown.
- **Rollback plan:** Remove the `SyncLock` and its lock field. Single file, two added lines plus the indentation of the enclosed block.
- **Human decision required:** Three separate decisions, in this order.
  1. Whether to resolve the UI-thread blocking question first. Recommended yes; the lock should not land before it is answered.
  2. Which form the deterministic key should take. Note first what does not work: "expand once and reuse within the call" is already what the code does. `Macro.Expand` is called exactly once per call at `VideoScript.vb:287`, and `LastCode` holds the previous call's expansion, so the mismatch is across calls and no within-call change can fix it. Three candidates that do work, in increasing size. (a) Compare the unexpanded script text: store and compare the `GetScript()` output rather than the expanded output, keeping the expansion for the write only. Smallest edit, and the effect is that a script whose only change is a macro's value stops triggering a rewrite. (b) Mask the volatile macros out of the comparison key only, leaving every other difference significant. Narrower behavioral change but more code, and it must be updated whenever a new volatile macro is added, which is a maintenance trap. (c) Expand once for the whole encode: have the coordinator at `GlobalClass.vb:633` supply the expanded text and have the chunk workers reuse it instead of re-expanding. Fixes the chunk path precisely and leaves the roughly fifty other call sites untouched, at the cost of threading the value through. All three restore the short-circuit; they differ in when a legitimate edit triggers a rewrite, which is a product-behavior question rather than a correctness one.
  3. Whether to also remove the redundancy rather than only repair the guard. `GlobalClass.vb:633` already synchronizes before `Parallel.Invoke`, so the per-worker calls are redundant whenever the guard works. Suppressing them would touch ten `GetChunkEncodeActions` overrides and change behavior for non-chunk callers of `Encode`. It is not needed to fix the defect once the guard holds, and it is recorded here only so the option is not lost.
  4. Whether to approve restoring the two pinned NuGet packages so a managed fix can be verified locally at all. Without this, no managed fix can be compile-verified or probe-verified in this environment.
- **Remaining unknowns:** Whether the `Error <> ""` secondary trigger is reachable during a chunked encode, which would make the defect fire without any macro and which no proposed fix addresses. Whether chunk encoders can read different script contents, since with a volatile macro each worker writes a different script to the same path; `inferred`, not observed. How often real projects carry a volatile macro in filter code; the probe injected the trigger and measured nothing about its frequency. The UI-thread blocking question is now resolved and is no longer an unknown.
- **Outcome 2026-08-24:** The user chose candidate (a), compare the unexpanded script text, and approved the package restore. Implemented as commit `b37202b2` on `agent/chunk-sync-guard-fix` with two gates and a mutation proof. See `Docs/Review/Chunk-Encode-Synchronize-Fix.md`. The remaining unknowns above are unchanged by the fix and stay open.

## Tool download integrity

- **Area and files:** `Source/General/ToolUpdate.vb`, `Source/Forms/DownloadForm.vb`, the `DownloadURL` fields in `Source/General/Package.vb`.
- **Protected category:** Tool download, update, provenance, and executable selection.
- **Why the risk matters:** The updater turns a web page into executable dependencies. `Update()` fetches `Package.DownloadURL` with `HttpClient`, takes the first `href` ending in `.7z`, `.zip`, or `.exe` that survives the include and exclude filters, resolves a relative link against the page's host, downloads it to the Desktop with `WebClient` under a browser user agent and a Referer header, extracts it with the bundled 7-Zip, and accepts the result if a file named `Package.Filename` exists anywhere in the extracted tree. Nothing compares the archive to a published digest, checks a signature, pins the download host to the page host, or refuses plain HTTP. A replaced link on the vendor page, a compromised mirror, or a network position between the user and an `http://` host reaches `Source/bin/Apps` with the user's authority after three confirmations that show only file names and paths.
- **Current evidence:** Static trace of the two files on 2026-09-06 (`ToolUpdate.vb:24-45`, `47-66`, `68-125`, `127-186`; `DownloadForm.vb:6-18`). Deterministic counts over `Source/**/*.vb`: 160 `DownloadURL` assignments, 158 `https://`, 2 `http://` (`haali.su/mkv` at `Package.vb:87`, `avisynth.nl/index.php/EEDI2CUDA` at `Package.vb:1204`). No `Authenticode`, `X509`, `SHA256`, `SHA1`, or `checksum` use exists outside an x265 option list, a CRC32 audio-track suffix, and an MD5 tip-key helper. `StaxRipUpdate.vb` (the application's own update) uses the GitHub releases API over HTTPS, which is a separate and narrower path. No download was executed in this pass. Confidence: verified for the code as read; `inferred` for the claim that no integrity control exists outside `Source`.
- **Smallest edit after approval:** Three independent, reversible changes, each small enough to review alone. (1) Refuse a `DownloadURL` or resolved link whose scheme is not `https`, and upgrade the two `http://` entries after confirming each host serves HTTPS. (2) Require the resolved link's host to match the `DownloadURL` host unless the package declares an allowed download host. (3) Compute the SHA-256 of the downloaded archive before extraction, show it in the "Copy new files?" dialog beside the file name, and write it to the log, so a user can compare it with the publisher's checksum and a support report carries it.
- **What could break:** (1) A vendor page that still links plain-HTTP archives would stop updating through StaxRip until the entry is corrected. (2) Vendors that host archives on a CDN or GitHub while the page lives elsewhere need an allowed-host entry, or their update breaks; a scan of the 160 entries for cross-host links is the first verification step. (3) Nothing functional; one extra hash pass over the archive.
- **Verification plan:** A static scan of every `DownloadURL` host against its likely archive host, reading the pages offline where a cached copy exists. Then the isolated update sandbox the coverage ledger already names: a local HTTPS listener serving a synthetic page and archive, one run per change, asserting refusal of `http://`, refusal of a cross-host link, and the displayed hash matching the served bytes. No live vendor download.
- **Rollback plan:** Each change is one commit touching `ToolUpdate.vb` or `DownloadForm.vb`; revert independently.
- **Human decision required:** Approve all three, a subset, or none. (3) alone adds visibility without changing behavior and is the safest first step if the maintainer's intent for mirrors is unknown.
- **Remaining unknowns:** Whether any vendor page intentionally links to another host; whether the two `http://` hosts serve HTTPS; whether the upstream maintainer wants integrity checks in the updater at all.

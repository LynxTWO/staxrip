01 / Working agreement

Start with the actual contract

StaxRip is a Windows desktop orchestrator, a native frame bridge, and a large portable tool distribution. A compile pass covers only one layer.

Preserve user authority

Use synthetic media and isolated settings. Do not touch user processes, media, queues, or release destinations.

Separate observations

Label behavior configured, inferred, fixture-tested, or unbounded. Do not turn a narrow result into “fully tested.”

Prefer reviewable patches

One behavior and one proof packet per PR is easier to merge than a broad cleanup with hidden dependencies.

X64 is the supported platform.Documentation rejects 32-bit Windows, root build/release scripts request x64, update assets are x64, and the staged Phase 1/2 changes retire remaining project/runtime branches.
02 / Workstation

Prepare a reproducible Windows build

  • Visual Studio or Build Tools with MSBuild, Visual C++ v143, and a compatible Windows SDK.
  • .NET Framework 4.8 reference assemblies and packages from Source/packages.config.
  • Official VapourSynth headers expected below the ignored prepared Source/bin/Apps tree.
  • A complete portable release tree only for real runtime, GUI, or packaging gates.
A clean clone is not a complete distributable.The ignored Apps tree is not reconstructed by tracked scripts. Restore declared packages and reviewed headers in an isolated worktree; never commit downloaded runtime trees.

Release mapping caveat

The solution's x64 Release maps managed StaxRip to Debug while FrameServer uses Release. Intent is open; do not change it incidentally.

AutoCrop artifact caveat

Release x64 writes a tracked binary path. Inspect hashes/status and never commit incidental generated drift.

07 / Native boundary

Treat FrameServer as ABI plus lifetime

  • Preserve COM-visible field widths and export names unless a migration is approved.
  • Check every int64_t/ptrdiff_t to 32-bit conversion.
  • Release acquired frames on all failure paths; clear returned pointers and pitch.
  • Keep loader state, module ownership, retry, sequential, and overlap behavior consistent.
  • Test controlled failures, then the exact packaged runtime layout.
VapourSynth lessonA process-wide entry point cannot safely depend on a per-instance handle that unloads after the first server. The accepted repair retains the validated module until process exit.

See FrameServer Runtime Gate.

08 / Portable operation

Test the app people run

The official portable archive was hash-verified and overlaid with the candidate. Settings were redirected to scratch and restored. GUI source opening passed for AVC/AAC, VP9/Opus, 10-bit FFV1/PCM, and VFR FFV1.

What's New is modal.After an update, an owned changelog window blocks the main form. Its custom OK button may not appear as a normal automation button; identify the exact title and use the default action.

For deterministic command-line loading: template first, project options second, media last. Reversing the first two can correctly trigger “Save changed project?”

11 / Evidence

Write a compact proof packet

  • Record commit, toolchain, platform, fixture, command, exit code, and first failure.
  • State source-only, packaged runtime, GUI, soak, or release-equivalent scope.
  • Remove user paths, media names, tokens, and raw private logs.
  • Bind downloaded archives and candidate artifacts with hashes.
  • Update unknowns when evidence resolves them; preserve the original concern.

12 / Collaboration

Make upstream work useful even without a reply

  1. Search prior issues/PRs and cite the exact context.
  2. Open a small draft with one behavior and reproducible evidence.
  3. Declare dependencies and merge order; do not hide stacked commits.
  4. Respond to review but avoid repeated pings to an inactive maintainer.
  5. Refresh while useful; otherwise maintain the fork and document divergence.
  6. Close or supersede stale alternatives so future contributors can follow history.
